# REST usage by command

[← README](../README.md) | [rest.md](rest.md) | [github-api.md](github-api.md)

This page is **what each command spends** against GitHub's REST `core` pool on the REST transport (`--transport rest`, `github.transport: rest`, or `auto` in a Claude Code cloud session or after a GraphQL fallback). GraphQL points are on [graphql-usage.md](graphql-usage.md). The REST calls GraphQL mode makes are listed in [graphql.md](graphql.md#rest-calls-in-graphql-mode).

`core` is metered in requests per hour (5,000 for a typical user token). Every snapshot `GET` whose route returns an ETag is conditional (see [conditional reads](rest.md#conditional-reads)): a `304 Not Modified` costs nothing, so a request count is an upper bound and the charged count is the number of those reads whose resource changed. The exception is a Claude Code cloud session's `GET /pulls/{n}/ccr/review_threads`: it sends no ETag, so it is sent fresh on every tick, but the proxy answers it without `X-RateLimit-*` headers and it is not metered against `core` (observed in a cloud run; see [rest.md](rest.md#claude-code-proxy-routes-and-unsupported-operations)). `--verbose` prints `apiUsage.rest.<resource>.requestCount` (charged) and `notModified` (304s), and counts responses without rate-limit headers, such as that read, as `apiUsage.unmeteredRestRequestCount` (text: `REST requests without rate-limit headers (unmetered): N`); those figures are authoritative for a live run.

## One PR

| Tick                                                                   | Requests sent | Charged                                                                                                                     |
| ---------------------------------------------------------------------- | ------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Cold cache (first tick in a state directory)                           | 14            | 13 (the closing pull re-read is a 304)                                                                                      |
| `pr-shepherd [PR]` / `poll`, unchanged continuation tick               | 14            | 0; the stored report is reused                                                                                              |
| Tick returned to the caller, `iterate`, MCP `iterate`, nothing changed | 14            | 0; the report is rebuilt from 304 bodies                                                                                    |
| Base branch moved                                                      | 14            | 1 (`GET /branches/{base}`)                                                                                                  |
| CI settles to a READY candidate                                        | 14 + 1        | 1 (check runs) when `mergeable_state` did not change; 2 when it did (the snapshot pull read is a 200 and the refresh a 304) |
| Merged PR (a closed, unmerged PR reads the full snapshot)              | 1             | 1 (the pull; cloud sessions too)                                                                                            |
| Base push makes the PR conflict                                        | 14 + 1        | 3 (the pull, `GET /branches/{base}`, and the merged-base lookup `GET /pulls?head=...`)                                      |
| READY tick after an unchanged READY tick (ready delay elapses)         | 14 + 1        | 0; the READY report is rebuilt from 304 bodies                                                                              |
| Changed tick, general case                                             | 14            | only the reads whose resource changed                                                                                       |
| Claude Code cloud session, any of the above except a merged PR         | +1            | +0; `ccr/review_threads` carries no ETag but is unmetered (`unmeteredRestRequestCount`)                                     |

Unlike GraphQL, where every tick returned to the caller pays for `BatchPr`, a REST tick that rebuilds its report still charges only the reads that changed.

The snapshot reads are listed in [rest.md](rest.md#snapshot-coverage). The 14 reads assume one page per list and a base branch summary that reports `protection.enabled: false`; each extra page of a list endpoint is one more read, and a protected base adds `GET /branches/{base}/protection`. A list whose last page holds exactly 100 items is re-read without a validator on every tick (see [conditional reads](rest.md#conditional-reads)), so it adds one sent and one charged read even when nothing changed.

Supplements on a tick, each one request unless noted:

- Annotations: one read per uncached completed check run that reports annotations, plus one per extra page past 100 annotations (_modeled_ in the token bench's `annotationBatchApi`).
- Failed job log excerpt: the run's jobs list (more pages past 100 jobs) and the job log, the same two requests as on GraphQL.
- Check blockers: one `GET /issues/{n}` or `GET /pulls/{n}` per distinct blocker while a matching check is failing.
- READY candidate: one live mergeability `GET /pulls/{n}` before acting. It is conditional and shares the pull's ETag, so it is a free 304 unless the pull changed since the snapshot read it.
- Mark-ready: one `POST /pulls/{n}/ccr/ready_for_review` in a cloud session (counted as charged here; whether the proxy meters it is unverified). Standard REST has no ready-for-review route and escalates `transport-unsupported` instead.
- Rule auto-resolve: one `POST /pulls/{n}/ccr/comments/{id}/resolve` per thread matched by a classification rule, in a cloud session (counted as charged; metering unverified). When any succeed, the journal update follows: a pull read, then a `PATCH /pulls/{n}` when the body changes. Rule auto-minimize is unsupported on REST.

A non-root native-stack layer's one-PR tick also reads the stack, the trunk's branch summary, rules, and compare (plus `GET /branches/{trunk}/protection` when the trunk's summary reports protection enabled), and the stack topology (the stack list and stack read twice, each layer's pull, and the viewer): 9 + stack size more requests sent (10 + stack size with a protected trunk). The topology reads are conditional and share the layer's ETag cache, so on a cold cache only the stack read, the trunk reads, and the other layers' pulls are charged: 3 + stack size more than a one-PR tick (16 + stack size in all, one more with a protected trunk). When GitHub has retargeted the layer onto the trunk after its parent merged, the trunk's branch summary and rules are the base's and answer 304 (14 + stack size charged in all). An unchanged later tick charges none of them (cloud: only `ccr/review_threads`). `routedLayerTickApi` in `evals/tokens/scenarios.mjs` models the cold cost.

## Several PRs

`pr-shepherd --stack PR` and `pr-shepherd` with two or more PRs read the summary, not per-layer snapshots.

A `--stack` summary shares evidence across layers within one tick ([rest.md](rest.md#shared-stack-tick-evidence)): the repository and the viewer are read once, stack membership is read before and after the layers to reject a moving stack, and branch policy is read once per distinct target branch. The table below covers that path.

An explicit list of PRs (`pr-shepherd 12 34 56`) shares only the viewer. Each PR reads its own repository settings, stack lookup, and branch policy, so a tick sends about 1 + 13 × N requests for single-page lists and unprotected bases (one more unmetered `ccr/review_threads` read per PR in a cloud session), and conditional reads keep an unchanged tick at 0 charged (_modeled_ from `src/github/rest-explicit-summary-read.mts`; no boundary test asserts it).

| Tick                                        | Requests sent                    | Charged                                    |
| ------------------------------------------- | -------------------------------- | ------------------------------------------ |
| 10-layer stack, no validators               | 126 (136 in a cloud session)     | 126 (cloud reads are unmetered)            |
| 10-layer stack, cold cache                  | 126                              | 104 (repeat reads inside the tick are 304) |
| 10-layer stack, unchanged                   | 126                              | 0                                          |
| 10-layer stack, one shared resource changed | 126                              | 1                                          |
| N-layer stack, no validators (_modeled_)    | 6 + 12 × N (6 + 13 × N in cloud) | 6 + 12 × N                                 |
| N-layer stack, unchanged, cloud (_modeled_) | 6 + 13 × N                       | 0 (N unmetered `ccr/review_threads` reads) |

The tests pin the shared reads (the repository and the viewer once, the stack lookup and stack read twice each, and one branch summary and rules read per distinct target branch) and the per-layer feedback reads (the pull three times, review comments, issue comments, and reviews once each). The rest of each layer's budget is its CI and branch-policy reads. In a cloud session each layer also reads `ccr/review_threads`, which is unmetered. `6 + 12 × N` is the token bench's linear fit to the 10-layer count, not a per-endpoint breakdown.

| `apply review` / `resolve`, with reply IDs                                  | Transcript read (review comments, issue comments, reviews, viewer; plus `ccr/review_threads` in cloud), then per reply the viewer, the review comments, and the reply POST. The counts assume each list fits on one page; each extra page of review comments, issue comments, or reviews adds one read to the transcript, and each extra page of review comments adds one read per reply | 4, plus 3 per reply, single-page baseline (_modeled_); cloud adds 1 unmetered read |
| `apply review` / `resolve`, resolve IDs                                     | `POST /pulls/{n}/ccr/comments/{id}/resolve` in a cloud session; unsupported on standard REST                                                                                                                                                                                                                                                                                             | 1 write per thread (metering unverified), plus any read to locate the thread root  |
| `apply review` / `resolve`, dismiss IDs                                     | `PUT /pulls/{n}/reviews/{id}/dismissals`                                                                                                                                                                                                                                                                                                                                                 | 1 write per review, plus any read to map the review ID                             |
| `apply review` / `resolve`, minimize IDs                                    | unsupported; reported as an error or one-look skip                                                                                                                                                                                                                                                                                                                                       | 0                                                                                  |

`log-file`, `admin log-file`, `journal extract`, MCP `extract_journal`, and `clean` / `admin clean` with an explicit PR number or the `repo` or `all` target do not call GitHub. `clean` / `admin clean` with `pr` and no number, `branch`, or `current` resolve the PR with the paged `GET /pulls?state=open` scan above, even with `--dry-run`.

The review-mutation rows are success-path costs. A reply POST with an ambiguous network or 5xx result re-reads the review comments to recover the reply. A reply, resolve, or dismissal denied with 403 or 404 triggers one full feedback read (4 requests plus extra pages; cloud adds the unmetered CCR thread read), plus the thread-root lookup for a reply or resolve, so the denied item becomes a one-look skip.
