# REST usage by command

[← README](../README.md) | [rest.md](rest.md) | [github-api.md](github-api.md)

This page is **what each command spends** against GitHub's REST `core` pool on the REST transport (`--transport rest`, `github.transport: rest`, or `auto` in a Claude Code cloud session or after a GraphQL fallback). GraphQL points are on [graphql-usage.md](graphql-usage.md). The REST calls GraphQL mode makes are listed in [graphql.md](graphql.md#rest-calls-in-graphql-mode).

`core` is metered in requests per hour (5,000 for a typical user token). Every snapshot `GET` whose route returns an ETag is conditional (see [conditional reads](rest.md#conditional-reads)): a `304 Not Modified` costs nothing, so a request count is an upper bound and the charged count is the number of those reads whose resource changed. The exception is a Claude Code cloud session's `GET /pulls/{n}/ccr/review_threads`, which sends no ETag and is charged on every tick, changed or not. `--verbose` prints `apiUsage.rest.<resource>.requestCount` (charged) and `notModified` (304s); that figure is authoritative for a live run.

## Where the numbers come from

The counts below are asserted at the HTTP boundary by these tests. Each fake server answers like GitHub's conditional reads, so a request is charged exactly when it is not a 304. Change the test and this page together.

| Test                                                                                                                                                | What it asserts                                                                                                                        |
| --------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `src/github/rest-wait-tick-cost.test.mts` "charges the cold snapshot once and nothing on unchanged wait ticks"                                      | One-PR tick: 14 reads, 13 charged cold (the closing pull re-read is a 304); unchanged continuation and returned ticks: 0 charged of 14 |
| `src/github/rest-wait-tick-cost.test.mts` "charges only the validator-less cloud thread read on unchanged cloud wait ticks"                         | Cloud unchanged tick: only `ccr/review_threads` is charged                                                                             |
| `src/github/rest-wait-tick-cost.test.mts` "does not replay the report when only the base branch moved"                                              | A base push: only `GET /branches/{base}` is charged                                                                                    |
| `src/github/rest-wait-tick-cost.test.mts` "charges only the changed check read on the tick where CI settles"                                        | CI settles: the check-runs read plus the READY candidate's mergeability pull read                                                      |
| `src/github/rest-wait-tick-cost.test.mts` "charges nothing on an unchanged 10-layer stack summary tick"                                             | 10-layer stack: 104 charged cold, 0 unchanged, 1 when one shared resource changes                                                      |
| `src/github/rest-stack-summary-sharing.test.mts` "keeps complete 10-layer snapshots within the HTTP request budget"                                 | 10-layer stack without validators: 126 requests, 136 in a cloud session                                                                |
| `src/commands/iterate/check-blocker-gate.rest.test.mts` "reads raw issue/pull state, deduplicates shared blockers and releases merged dependencies" | One `GET` per distinct check blocker                                                                                                   |
| `src/commands/iterate/mark-ready.rest.test.mts` "attempts cloud ready-for-review with unknown capability and trusts draft:false"                    | Cloud mark-ready: one request, the `ccr/ready_for_review` POST                                                                         |

The token bench models the same counts for whole sessions (`evals/tokens/lib.mjs`: `SHEPHERD_TICK_API_REST`, `SHEPHERD_TICK_API_CLOUD`, `stackTickApiRest`, `stackTickApiCloud`), and records a live cross-check in `evals/tokens/data/api-usage-check.json`: on #548, 16 charged requests on a cold first tick (13 snapshot reads and three annotation reads), plus one free 304 for the pull re-read, then 0 charged requests with 14 not-modified reads on the unchanged second tick. Rows below marked _modeled_ come from that bench rather than a boundary test.

## One PR

| Tick                                                                   | Requests sent | Charged                                              |
| ---------------------------------------------------------------------- | ------------- | ---------------------------------------------------- |
| Cold cache (first tick in a state directory)                           | 14            | 13 (the closing pull re-read is a 304)               |
| `pr-shepherd [PR]` / `poll`, unchanged continuation tick               | 14            | 0; the stored report is reused                       |
| Tick returned to the caller, `iterate`, MCP `iterate`, nothing changed | 14            | 0; the report is rebuilt from 304 bodies             |
| Base branch moved                                                      | 14            | 1 (`GET /branches/{base}`)                           |
| CI settles to a READY candidate                                        | 14 + 1        | 2 (check runs, then the live mergeability pull read) |
| Changed tick, general case                                             | 14            | only the reads whose resource changed                |
| Claude Code cloud session, any of the above                            | +1            | +1 (`ccr/review_threads` carries no ETag)            |

Unlike GraphQL, where every tick returned to the caller pays for `BatchPr`, a REST tick that rebuilds its report still charges only the reads that changed.

The snapshot reads are listed in [rest.md](rest.md#snapshot-coverage). The 14 reads assume one page per list and a base branch summary that reports `protection.enabled: false`; each extra page of a list endpoint is one more read, and a protected base adds `GET /branches/{base}/protection`. A list whose last page holds exactly 100 items is re-read without a validator on every tick (see [conditional reads](rest.md#conditional-reads)), so it adds one sent and one charged read even when nothing changed.

Supplements on a tick, each one request unless noted:

- Annotations: one read per uncached completed check run that reports annotations, plus one per extra page past 100 annotations (_modeled_ in the token bench's `annotationBatchApi`).
- Failed job log excerpt: the run's jobs list (more pages past 100 jobs) and the job log, the same two requests as on GraphQL.
- Check blockers: one `GET /issues/{n}` or `GET /pulls/{n}` per distinct blocker while a matching check is failing.
- READY candidate: one live mergeability `GET /pulls/{n}` before acting.
- Mark-ready: one `POST /pulls/{n}/ccr/ready_for_review` in a cloud session. Standard REST has no ready-for-review route and escalates `transport-unsupported` instead.
- Rule auto-resolve: one `POST /pulls/{n}/ccr/comments/{id}/resolve` per thread matched by a classification rule, in a cloud session. When any succeed, the journal update follows: a pull read, then a `PATCH /pulls/{n}` when the body changes. Rule auto-minimize is unsupported on REST.

A non-root native-stack layer's one-PR tick also reads the stack, the trunk's branch protection, rules, and compare, and the stack topology (the stack list and stack read twice, each layer's pull, and the viewer): about 9 + stack size more reads on a cold cache (_modeled_, `routedLayerTickApi` in `evals/tokens/scenarios.mjs`).

## Several PRs

`pr-shepherd --stack PR` and `pr-shepherd` with two or more PRs read the summary, not per-layer snapshots.

A `--stack` summary shares evidence across layers within one tick ([rest.md](rest.md#shared-stack-tick-evidence)): the repository and the viewer are read once, stack membership is read before and after the layers to reject a moving stack, and branch policy is read once per distinct target branch. The table below covers that path.

An explicit list of PRs (`pr-shepherd 12 34 56`) shares only the viewer. Each PR reads its own repository settings, stack lookup, and branch policy, so a tick sends about 1 + 13 × N requests for single-page lists and unprotected bases (one more per PR in a cloud session), and conditional reads keep an unchanged tick at 0 charged (N in cloud) (_modeled_ from `src/github/rest-explicit-summary-read.mts`; no boundary test asserts it).

| Tick                                        | Requests sent                    | Charged                                    |
| ------------------------------------------- | -------------------------------- | ------------------------------------------ |
| 10-layer stack, no validators               | 126 (136 in a cloud session)     | 126 (136)                                  |
| 10-layer stack, cold cache                  | 126                              | 104 (repeat reads inside the tick are 304) |
| 10-layer stack, unchanged                   | 126                              | 0                                          |
| 10-layer stack, one shared resource changed | 126                              | 1                                          |
| N-layer stack, no validators (_modeled_)    | 6 + 12 × N (6 + 13 × N in cloud) | same                                       |
| N-layer stack, unchanged, cloud (_modeled_) | 6 + 13 × N                       | N (one `ccr/review_threads` per layer)     |

The tests pin the shared reads (the repository and the viewer once, the stack lookup and stack read twice each, and one branch summary and rules read per distinct target branch) and the per-layer feedback reads (the pull three times, review comments, issue comments, and reviews once each). The rest of each layer's budget is its CI and branch-policy reads. In a cloud session each layer also reads `ccr/review_threads`. `6 + 12 × N` is the token bench's linear fit to the 10-layer count, not a per-endpoint breakdown.

The counts assume each list fits on one page; each extra page of review comments, issue comments, or reviews adds one read to the transcript, and each extra page of review comments adds one read per reply | 4 (5 in cloud), plus 3 per reply, single-page baseline (_modeled_)                     |

| `apply review` / `resolve`, minimize IDs                                    | unsupported; reported as an error or one-look skip                                                                                                                                                                                                                                                                                                                                       | 0                                                                                      |

| No PR number passed                                                         | `GET /pulls?state=open`, paged, matched by head branch                                                                                                                                                                                                                                                                                                                                   | 1 per 100 open PRs                                                                     |

`log-file`, `admin log-file`, `journal extract`, MCP `extract_journal`, and `clean` / `admin clean` with an explicit PR number or the `repo` or `all` target do not call GitHub. `clean` / `admin clean` with `pr` and no number, `branch`, or `current` resolve the PR with the paged `GET /pulls?state=open` scan above, even with `--dry-run`.

The review-mutation rows are success-path costs. A reply POST with an ambiguous network or 5xx result re-reads the review comments to recover the reply. A reply, resolve, or dismissal denied with 403 or 404 triggers one full feedback read (4 requests, 5 in cloud, plus extra pages), plus the thread-root lookup for a reply or resolve, so the denied item becomes a one-look skip.
